# Storage Migrations Specification

## Purpose

Replace the current ad-hoc schema bootstrap (`Base.metadata.create_all`) with
Alembic-managed migrations so that schema evolution is version-controlled,
reversible, idempotent, and auditable. This spec defines the runtime contract,
CLI surface, compatibility guarantees, and verifiable acceptance criteria
backing the change introduced in Phase A task A.1.

## Scope

**In scope**:
- Alembic configuration (`alembic.ini` at repo root, `alembic/env.py`,
  `alembic/versions/`).
- Initial migration `0001_initial_schema` autogenerated from
  `puma.storage.models.Base.metadata`.
- Refactor of `puma db` CLI from single argument-dispatch (`db <action>`) to a
  sub-Typer with explicit `migrate`, `downgrade`, `history`, `status`
  subcommands.
- Re-wiring of `puma.storage.db.init_db()` to invoke Alembic programmatically
  in place of `Base.metadata.create_all`.
- Integration tests covering upgrade/downgrade lifecycle, idempotence,
  CLI delegation, schema parity with the ORM, and error surfacing for
  missing configuration.

**Out of scope**:
- Migration data backfills (column population, value transformations). Future
  spec when the first non-cosmetic schema change ships.
- Multi-database support (PostgreSQL, MySQL). PUMA targets SQLite at
  `data/puma.db` for v2.x.
- Online-migration safety analysis. Single-process sqlite, no concurrency
  contract beyond what SQLAlchemy already provides.
- Async/CI-driven migration gating. Phase A.2 wires CI on `develop`; Alembic
  test execution piggybacks on the existing pytest suite.

## Architecture

### Filesystem layout

```
puma/
├── alembic.ini                    # config root (sqlalchemy.url, script_location)
├── alembic/
│   ├── env.py                     # online/offline migration entrypoints
│   ├── script.py.mako             # template for new revisions
│   └── versions/
│       └── 0001_initial_schema.py # baseline schema (autogenerated)
└── src/puma/
    ├── cli.py                     # db_app sub-Typer (migrate/downgrade/history/status)
    └── storage/
        └── db.py                  # init_db() delegates to alembic.command.upgrade
```

### `alembic/env.py`

- Imports `puma.storage.models.Base` and exposes `target_metadata =
  Base.metadata`.
- `compare_type=True` and `compare_server_default=True` enabled so future
  autogenerate runs detect type changes and default-value drift.
- `run_migrations_online` uses `engine_from_config` with `pool.NullPool` to
  avoid leaking connections in tests.
- `run_migrations_offline` supports SQL-dump generation (`alembic upgrade
  head --sql`) for review workflows.

### `puma db` CLI

The current implementation is a single command dispatching by string
argument:

```python
@app.command()
def db(action: str = "migrate", db_path: str = "data/puma.db") -> None:
    if action == "migrate": ...
    elif action == "status": ...
    else: typer.Exit(1)
```

The replacement is a sub-Typer with discrete commands:

| Subcommand | Behavior |
|------------|----------|
| `puma db migrate [revision]` | `alembic upgrade <revision>` (default `head`). |
| `puma db downgrade [revision]` | `alembic downgrade <revision>` (default `-1`). |
| `puma db history` | `alembic history` — revision chain inspection. |
| `puma db status` | Preserves the current behavior: prints DB path, file size if present, and "not found" guidance otherwise. **Does NOT delegate to `alembic current`** (decision S1, see Edge cases). |

The `--db` option (path override, default `data/puma.db`) is preserved on the
subcommands that interact with the filesystem (`migrate`, `downgrade`,
`status`).

### `puma.storage.db.init_db()`

Single source of truth for "ensure DB ready for queries". Replaces direct
`Base.metadata.create_all(_engine)` with programmatic
`alembic.command.upgrade(cfg, "head")` (decision I3).

Pseudocode:

```python
def init_db(db_path: Path | str = _DEFAULT_DB) -> None:
    global _engine, _SessionLocal
    path = Path(db_path)
    path.parent.mkdir(parents=True, exist_ok=True)
    url = f"sqlite:///{path}"

    cfg = _alembic_config_for(url)        # raises if alembic.ini missing
    command.upgrade(cfg, "head")           # idempotent

    _engine = create_engine(url, connect_args={"check_same_thread": False})
    _SessionLocal = sessionmaker(bind=_engine, autoflush=False, autocommit=False)
```

`_alembic_config_for(url)` resolves `alembic.ini` from CWD, raises a clear
exception if missing (see AC-08), and overrides `sqlalchemy.url` so the same
function works with arbitrary DB paths (tests, CLI `--db` flag).

## Acceptance criteria

Each criterion maps 1:1 to an integration test in
`tests/integration/test_alembic_migrations.py` (created in A.1.7, BEFORE
implementation, per rule §0.6).

| ID | Test name | Asserts |
|----|-----------|---------|
| AC-01 | `test_upgrade_from_empty_db` | `alembic upgrade head` from an empty SQLite file populates exactly the set `Base.metadata.tables.keys() ∪ {"alembic_version"}`. Verified via `sqlalchemy.inspect(engine).get_table_names()`. |
| AC-02 | `test_downgrade_base` | `alembic downgrade base` removes all ORM tables. Empirical observation (A.1.5/A.1.7 with Alembic 1.18.4): `alembic_version` persists as a table with **0 rows** after `downgrade base`. The assert reflects this observed behavior; future Alembic versions that drop the table entirely instead of clearing it would require updating this test alongside the Alembic upgrade. |
| AC-03 | `test_downgrade_then_upgrade_idempotent` | After `downgrade base` followed by `upgrade head`, the table set and per-table column set are bit-equivalent to the post-initial-upgrade state. Compares table names and `inspect(engine).get_columns(t)` per table. |
| AC-04 | `test_double_upgrade_head_is_noop` | `upgrade head` invoked twice consecutively does not raise and does not modify schema. Asserts that table set and the row of `alembic_version` are identical pre/post second invocation. |
| AC-05 | `test_cli_db_migrate_delegates_to_alembic` | Invoking `puma db migrate` against an empty DB produces the same schema as `alembic upgrade head` directly. **Asserts `Base.metadata.create_all` is NOT called** during this path (verified via `unittest.mock.patch` or import-time introspection of the call graph). |
| AC-06 | `test_cli_db_status_preserved` | `puma db status` after refactor still emits the informative output documented in `docs/user_guide.md` (DB path, size if present, "not found" guidance otherwise). The exact assert string is fixed from the current implementation, not invented. (Decision S1.) |
| AC-07 | `test_init_db_invokes_alembic_and_callers_unaffected` | `init_db()` populates `alembic_version` with the head revision after running on an empty DB. Sub-asserts: (a) calling `init_db()` then a trivial query against `runs` (mirrors `orchestrator/runner.py:48`) does not raise; (b) calling `init_db()` then a trivial query against `metrics` (mirrors `orchestrator/compare.py:13`) does not raise. (Decision I3.) |
| AC-08 | `test_init_db_raises_on_missing_alembic_ini` | Running `init_db()` from a CWD where `alembic.ini` does not exist raises an exception whose message contains `"alembic.ini"` and `"not found"` (or equivalent). **No silent fallback to `Base.metadata.create_all`.** |
| AC-09 | `test_initial_migration_matches_orm_schema` | After `upgrade head` on an empty DB, for every table declared in `Base.metadata.tables` and for every column within it, the migration result matches the ORM declaration on: **(a)** type family asserted via `isinstance(actual.type, type(orm.type))` to accept dialectal concretions (e.g., SQLite reports `String` columns as `VARCHAR`, which is a subclass of `String` in SQLAlchemy). This still detects real type-family changes (`String → Integer` would fail `isinstance`); **(b)** nullability, `column.nullable == orm_column.nullable`; **(c)** primary-key membership, `column.primary_key == orm_column.primary_key`; **(d)** foreign keys: matching set of `(referred_table, referred_column)` tuples per column; **(e)** parameterized type attributes (`length` for `String`, `precision`/`scale` for `Numeric`/`Float`) — compared **only when the ORM declared them explicitly**. If the ORM column omits a parameter, the migration is not required to set it. Detects silent schema drift (NOT NULL added, FK retargeted, type family changed) without false negatives from SQLite type-name reporting. |
| AC-10 | `test_initial_migration_has_no_pending_changes` | Programmatic equivalent of `alembic check`: build a `MigrationContext` with `compare_type=True` and `compare_server_default=True`, request `produce_migrations(...)`, and assert the resulting `MigrationScript.upgrade_ops` is empty. Guarantees `0001_initial_schema` is a complete, lossless capture of the current ORM. |

## Compatibility

`puma.storage.db.init_db()` is currently called from two production sites
beyond the CLI:

| Caller | File:line | Contract from caller's perspective |
|--------|-----------|------------------------------------|
| `RunOrchestrator.__init__` | `src/puma/orchestrator/runner.py:48` | "After `init_db(db_path)`, the SQLAlchemy session factory is wired and the schema is ready for inserts/selects." |
| `compare_runs(...)` | `src/puma/orchestrator/compare.py:13` | Same contract. |

**Compatibility guarantee**: this spec preserves both contracts. `init_db()`
continues to produce a session-ready, schema-applied DB. The substitution of
`Base.metadata.create_all` with `command.upgrade(cfg, "head")` is transparent
to callers — both produce a state where `Base.metadata.tables.keys()` are
all present and queryable.

The only observable change for callers is that `init_db()` now requires
`alembic.ini` to be reachable from the process CWD (or an environment with
the Alembic config explicitly located). Both call sites already run from
the repository root in production paths (CLI and Docker entrypoint), so
this constraint is satisfied without changes.

## Edge cases & decisions

### Decision S1 — Preserve `puma db status`

**Decision**: keep `puma db status` as a fourth subcommand of the new
`db_app`, retaining the current implementation (filesystem stat + guidance
message). Do **not** delegate to `alembic current` even though that command
returns adjacent information.

**Rationale**:
- `puma db status` is documented in `docs/user_guide.md` (lines 479, 688)
  and `docs/troubleshooting.md` — removing it would be a public-API break
  not contemplated in PROMPT-A.md A.1.6.
- The current output (DB path + size or "not found") is more useful to
  end-users than the Alembic revision hash returned by `alembic current`.
  The two answer different questions ("does my DB file exist and how big
  is it?" vs. "what schema revision am I on?").
- Migration revision visibility is already provided by `puma db history`.

### Decision I3 — `init_db()` invokes Alembic programmatically

**Decision**: `init_db()` calls `alembic.command.upgrade(cfg, "head")`
in place of `Base.metadata.create_all(_engine)`. There is no fallback to
`create_all`.

**Rationale**:
- Single source of truth: schema state is determined by the migration
  chain, never by ORM introspection at runtime. Avoids drift between
  ORM declarations and the actual DB.
- Idempotent on warm DBs: `upgrade head` is a no-op when already at head
  (verified by AC-04), preserving the existing call-site semantics
  ("safe to call repeatedly").
- Failure mode is explicit: if `alembic.ini` cannot be located, the
  caller learns immediately (AC-08) instead of silently creating a
  schema that diverges from the migration chain.

The cost is a hard dependency on `alembic.ini` being reachable. This is
accepted because the only environments calling `init_db()` are the CLI
and Docker entrypoint, both rooted at the repo.

### Behavior of `alembic_version` after `downgrade base`

**Status**: observed empirically during A.1.5/A.1.7. With Alembic 1.18.4,
the `alembic_version` table persists after `alembic downgrade base` and
holds **zero rows**. AC-02 asserts this behavior. Future Alembic versions
that change this convention (e.g., dropping the table entirely) will
require updating the assertion alongside the Alembic upgrade in the same
commit.

### Configuration discovery

`alembic.ini` is discovered from the process CWD. Tests use the
`alembic.config.Config` object directly with `set_main_option(
"sqlalchemy.url", ...)` to point at a `tmp_path` SQLite file, isolating
each test from `data/puma.db`.

## Verification

After A.1.5 and A.1.7 complete, the following commands must succeed:

```bash
# Tests (TDD-first per §0.6 — these are written before implementation
# in A.1.7, fail until A.1.2-A.1.6 land, then turn green).
pytest tests/integration/test_alembic_migrations.py -v
# Expected: 10 tests passed (AC-01 through AC-10).

# CLI surface preserved.
rm -f data/puma.db
puma db migrate
# Expected: "Database migrated to revision: head"

puma db status
# Expected: "data/puma.db: <size> KB"

puma db history
# Expected: lists 0001_initial_schema as the head revision.

puma db downgrade base
# Expected: "Database downgraded to revision: base"
```
