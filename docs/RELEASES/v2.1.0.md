# PUMA v2.1.0 Release Notes

**Release date:** 2026-05-10
**Previous release:** v2.0.0 (2026-05-10)
**Branches:** `develop` → `main` (fast-forward at tag time)

## Summary

This release consolidates **Phase B** (multi-model evaluation) and the
critical-debt cleanup of **Phase D Sprints 1 and 2**. The platform now
reports GPU energy correctly inside the container, has a complete
catalog single source of truth (SoT) for `(model → hardware profile)`
compatibility, and ships with a comparative analysis of 9 models across
3 PMO scenarios. Three critical methodological findings detected during
the release validation cycle (D15, D17, D18, D21) are resolved with
academic traceability preserved in `docs/known_debt.md`.

## Highlights

### Multi-model evaluation sweep

- 9 models compatible with the `gpu-entry` profile evaluated across
  the 3 PMO scenarios (`triage_jira`, `estimation_tawos`,
  `prioritization_jira`)
- 2,700 inferences total; ~67.5 Wh / 11.75 g CO₂ compute budget
- Best performers vary by task; small models (1B–3B) are competitive
  with larger ones on several PMO scenarios — see
  [docs/results/phase_b_analysis.md](../results/phase_b_analysis.md)
- Reproducible plot generation:
  `scripts/generate_phase_b_plots.py`

### CodeCarbon GPU detection

- Two coupled fixes applied: CDI GPU passthrough on `puma_runner`
  in `docker-compose.yml` plus
  `tracking_mode="process"` → `"machine"` in the orchestrator and
  the codecarbon wrapper
- Post-fix: `gpu_energy > 0` in emissions rows (was always 0 in
  v2.0.0). First non-zero row recorded in this release.
- Note: the 27 emissions rows from the B.3 sweep pre-date this fix
  and report only CPU+RAM energy; documented in
  [docs/HARDWARE.md](../HARDWARE.md) and
  [docs/results/phase_b_analysis.md](../results/phase_b_analysis.md)

### Catalog single source of truth

- `puma.preflight.catalog.models_for_profile()` derives profile
  compatibility from `config/models_catalog.yaml` dynamically
- Eliminated the `models[]` field from `config/profiles.yaml` (it
  duplicated information)
- 17 catalog / profiles drift pairs detected and resolved (F7)
- `gemma4` family excluded from `gpu-entry` based on empirical
  evidence: under CPU offload on 6 GB VRAM the Ollama detokenizer
  returns `raw_response=''` for structured prompts (D18 resolution)

### Technical debt cleanup

- **9 of 15** known debt items resolved in this release (60 %)
- Resolved: D1, D6, D10, D13, D15, D17, D18, D18-cleanup, D21
- Remaining: 6 items (0 critical, 5 medium, 1 low; one
  decided-no-action)
- Detailed evidence in
  [docs/known_debt.md](../known_debt.md) — see the new "Resolved
  technical debt" section for the involved Sprint 2 write-ups

### Methodological findings preserved (academic traceability)

- 8 closed findings F1–F8 from v2.0.0 validation
- 3 new findings from Phase B / Sprint 1 / Sprint 2 surfaced and
  resolved:
  - **D15** — infrastructure + measurement-method coupling (CDI
    passthrough AND `tracking_mode` had to be aligned)
  - **D21** — unit-test vs end-to-end discrepancy (catalog
    `timeout_s` declared but not consumed)
  - **D18** — symptom layer vs causal layer (the failure was at
    Ollama's detokenizer, not the PUMA parser; a parser fix would
    have been a dead end)

## Known limitations

- **Single hardware tier evaluated** (`gpu-entry`). Models requiring
  `gpu-mid`+ — `qwen2.5:14b`, `gemma3:12b` (catalog-compatible but
  with `timeout_s=1800` overhead), `deepseek-r1:14b`,
  `gemma4:{e4b, 26b-a4b}`, `llama3.1:70b` — are catalogued but not
  empirically evaluated in this release.
- **Single adaptation strategy** (`contextual-anchoring`) used in
  the main sweep; cross-strategy comparison is roadmap.
- **Single seed (42)** per cell; multi-seed validation with
  confidence intervals is roadmap.
- **GPU energy pre-D15**: the 27 B.3 sweep rows report only CPU+RAM
  energy; they are not directly comparable to post-D15 rows on the
  `gpu_energy` / `kwh` / `co2_kg` columns.
- **AMD ROCm and Apple Metal** backends are not yet detected
  (NVIDIA-only development hardware).
- **Test coverage at 57 %** for v2.1.0 (down from ≥70 % in v2.0.0
  due to new code in Phase B without proportional UI/reporting
  tests). Critical pipeline modules remain well-covered; the gap is
  concentrated in `puma.dashboard.*`, `puma.reporting.report`, and
  `puma.orchestrator.compare`, scheduled for refactor in the planned
  Phase C milestone.

## Upgrade notes

- **No breaking changes** for users of the public API.
- The `tracking_mode` change in CodeCarbon is internal; existing
  integrations are not affected.
- New users should run `git config core.hooksPath .githooks` after
  clone to enable the `.githooks/commit-msg` hook (strips
  `Co-Authored-By` trailers). Setup documented in
  [docs/CONTRIBUTING.md](../CONTRIBUTING.md).
- Anyone who depended on `Profile.models` should migrate to
  `puma.preflight.catalog.models_for_profile(profile_name)`.
